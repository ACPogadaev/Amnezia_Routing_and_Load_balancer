# Архитектура

## Поток пакета

Для VPN-клиента существуют два независимых пути:

```text
VPN client
   |
   v
existing AmneziaWG ingress container
   |-- destination NOT in target_v4 --> direct bridge --> public interface
   |
   `-- destination in target_v4 --> transit bridge --> host classifier
                                              |-- mark 0x201 --> egress 1
                                              |-- mark 0x202 --> egress 2
                                              |-- mark 0x203 --> egress 3
                                              `-- mark 0x2ff --> unreachable
```

Каждый egress — отдельный Docker-контейнер и отдельное network namespace. Внутри поднимается AWG-интерфейс из переданного пользователем клиентского профиля. Пересылаемый пакет SNAT-ится во внутренний адрес AWG-клиента и может выйти только через его AWG-интерфейс.

## Почему два слоя

Каталог `v2` создаёт базовую схему:

- отделяет прямой путь от transit-пути;
- загружает целевой набор одновременно на host и в ingress namespace;
- поднимает первый egress;
- устанавливает защиту от прямой утечки целевого трафика;
- сохраняет входной AWG-транспорт на его штатном Docker/DNAT-пути.

Каталог `v3` добавляет:

- второй и третий egress;
- host-level классификацию по 256 buckets;
- контроллер здоровья и нагрузки;
- отдельные policy tables/marks для каждого выхода.

Разделение сохраняет проверенный single-egress режим как точку отката.

## Марки и таблицы

В ingress namespace целевой пакет получает `0x101` и направляется в таблицу 301. На host новый conntrack получает одну из меток:

| Метка | Назначение | Таблица |
|---|---|---:|
| `0x201` | egress 1 | 401 |
| `0x202` | egress 2 | 402 |
| `0x203` | egress 3 | 403 |
| `0x2ff` | ни одного доступного выхода | `unreachable` |

После каждого `fwmark -> lookup` установлено правило с той же точной меткой и действием `unreachable`. Это не позволяет пакету провалиться в `main` при отсутствии маршрута в специализированной таблице.

## Стабильность соединений

Новый поток выбирает bucket по младшему байту IPv4-адреса назначения. Контроллер назначает 256 buckets здоровым выходам согласно рассчитанным весам. Выбранная метка записывается в conntrack; ответные и последующие пакеты используют тот же egress.

Изменение bucket map влияет только на новые соединения. Существующий TCP-поток не переносится на другой публичный IP, потому что такая миграция обычно разрушает сессию.

## Health-check и нагрузка

Контроллер проверяет для каждого выхода:

- контейнер запущен;
- AWG-интерфейс доступен;
- handshake достаточно свежий;
- внешний HTTP endpoint отвечает через адрес AWG-интерфейса;
- наблюдаемый внешний IP совпадает с `*_EXPECTED_EXIT_IP`;
- дополнительный TCP endpoint достижим.

Выход исключается после `HEALTH_FAILURE_THRESHOLD` последовательных ошибок и возвращается после `HEALTH_SUCCESS_THRESHOLD` успехов. EWMA скорости туннеля снижает долю новых buckets у более загруженного выхода, но не обещает точного деления полосы.

## Fail-closed

Защита строится несколькими независимыми слоями:

1. nftables guard блокирует неверные прямые пути;
2. policy `unreachable` стоит сразу после каждого lookup;
3. egress namespace запрещает вывод AWG-source не через AWG-интерфейс;
4. Docker `DOCKER-USER` разрешает только ожидаемые пары интерфейсов/адресов;
5. guard загружается до Docker через systemd dependency/drop-in;
6. набор и правила применяются одним `nft -f`, то есть транзакционно;
7. при ошибке обновления предыдущий активный ruleset остаётся на месте.

## Входной транспорт

Зашифрованный UDP-трафик входного AmneziaWG нельзя смешивать с расшифрованным клиентским трафиком. Ответный транспорт возвращается через тот же Docker-адрес, к которому DNAT направил входящий пакет. Внутри namespace он получает служебный DSCP tag; host guard допускает только точный tuple интерфейс/source/UDP source-port/tag. Клиентский трафик не может использовать этот путь как запасной прямой выход.

## Порядок старта

Guard является обязательной зависимостью Docker. Сначала загружается полный проверенный целевой набор и блокирующие правила, затем Docker получает возможность запускать ingress/egress. Если guard не загрузился, Docker не должен стартовать через эту цепочку зависимостей.

## Что не меняется

- клиентские профили для подключения к балансировщику;
- приватные ключи входного AmneziaWG;
- настройки трёх внешних VPN-серверов;
- маршруты трафика, чьи назначения отсутствуют в `target_v4`.
